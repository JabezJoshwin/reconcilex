# Senior backend review — 2026-10-13

Three independent read-only subagents reviewed financial/reconciliation correctness,
input validation/security, and tests/API/failure scenarios. The main agent reproduced
findings and implemented fixes. No HIGH finding was confirmed. Three MEDIUM issues
and one LOW regression-coverage gap were confirmed.

## MEDIUM: MVC client errors became HTTP 500

Original location: `backend/src/main/java/com/reconcilex/api/ApiExceptionHandler.java:21-22`.
The generic exception handler caught framework routing/protocol exceptions and discarded
their status and headers. Live probes of an unknown API route and unsupported method
returned 500 with `INTERNAL_ERROR`. Unsupported upload media type had the same code path.

Reproduce on the original revision:

```sh
curl -i http://localhost:18080/api/not-a-route
curl -i -X PUT http://localhost:18080/api/reconciliations
curl -i -X POST -H 'Content-Type: application/json' -d '{}' http://localhost:18080/api/reconciliations
```

Fix: `ApiExceptionHandler.java:21-37` handles framework 404/405/406/415 errors explicitly,
preserves protocol headers (including `Allow`), and leaves unexpected failures at 500.
406 has an empty body when JSON is not acceptable. Regression coverage:
`ApiWorkflowTest.java:76-81`.

## MEDIUM: cross-origin requests could persist local runs

Original location: `backend/src/main/java/com/reconcilex/api/SecurityHeaders.java:9-14`;
upload entry point `ReconciliationController.java:18-23`. Response CORS restrictions
alone do not reject simple multipart writes. A webpage on another loopback port can
attempt a no-cors FormData upload. Public-page-to-loopback browser protections vary;
this finding does not assume those protections can always be bypassed.

The main agent reproduced one foreign-Origin upload against the original running app:

```sh
curl -i -H 'Origin: http://localhost:19090' \
  -F internalFile=@sample-data/empty.csv \
  -F processorFile=@sample-data/empty.csv \
  http://localhost:18080/api/reconciliations
```

Observed 201 and a persisted empty run. No private transaction data was submitted.

Fix: `SecurityHeaders.java:14-36` rejects unsafe requests with foreign/opaque/malformed
Origin or incompatible Fetch Metadata before dispatcher multipart handling. Origin
scheme, host and effective port must match; requests without browser headers remain
supported for CLI use. This guard is not authentication. Regression coverage:
`ApiWorkflowTest.java:83-99`, including unchanged database counts and the legitimate
external Docker port.

## MEDIUM: vulnerable embedded Tomcat multipart cleanup

Original location: `backend/pom.xml:3` resolved Boot 3.5.6's Tomcat 10.1.46;
multipart enabled at `backend/src/main/resources/application.yml:6-9`.
[Apache's CVE-2025-61795 advisory](https://tomcat.apache.org/security-10.html#Fixed_in_Apache_Tomcat_10.1.47)
states that multipart errors can retain temporary files until GC, enabling disk
exhaustion. Apache rates this vulnerability LOW; the application review rates it MEDIUM
because accepting uploaded files is its central workflow. No RCE claim is made.

Safe evidence: cached dependency BOM and jars showed 10.1.46; the official advisory
confirmed applicability. Destructive repeated-upload/disk-exhaustion reproduction was
not executed. Such a reproduction would require an isolated constrained temporary disk,
repeated multipart requests that fail after writing a part, and file/storage inspection
before GC.

Fix: `backend/pom.xml:7-8` pins Tomcat 10.1.60 within the same compatible 10.1 line.
The official Maven Central artifact returned HTTP 200 before the change. Build and
real-container multipart-limit verification follow below.

## LOW: rollback test bypassed the service boundary

Original location: `backend/src/test/java/com/reconcilex/api/ApiWorkflowTest.java:82-93`.
The test manually wrapped repository writes in a TransactionTemplate. It would pass
if the actual service lost `@Transactional`; the actual annotation was present and no
corruption was found. Reproduce the coverage gap by inspecting the original test call
path: it never invokes `ReconciliationService.create`.

Fix: `ApiWorkflowTest.java:107-122` now injects an error after real inserts through a
repository spy while invoking the actual service proxy, then verifies all three table
counts remain unchanged. No application transaction behavior was changed.
